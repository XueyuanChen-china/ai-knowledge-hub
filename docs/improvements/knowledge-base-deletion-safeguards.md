# Knowledge Base Deletion Safeguards

## 这份文档解决什么问题

当前前端已经支持删除知识库。

但是后端第一版的删除逻辑还比较原始：

```text
DELETE /knowledge-bases/{id}
  -> 直接删除 knowledge_bases 主记录
```

这在真实项目里不够稳，因为一个知识库下面通常还会挂很多依赖数据，例如：

- documents
- knowledge_items
- chunks
- conversations
- messages
- review_tasks

如果没有明确的删除策略，就会出现两类问题：

1. 数据库外键直接拦截删除
2. 主记录删掉了，但下游数据残留或状态不一致

所以这一项必须作为后续升级点单独处理，不能只靠前端弹窗提示。

---

## 当前问题

### 1. 删除策略不明确

现在还没有正式定义：

- 是禁止删除非空知识库
- 还是允许级联删除
- 还是做软删除

这三种策略的影响完全不一样，必须先选清楚。

### 2. 后端缺少依赖检查

删除前至少应该知道这个知识库下面是否存在：

- 文档
- 知识条目
- chunk
- 会话记录

否则前端只能“试一下”，失败再把数据库错误回显出来，这不够产品化。

### 3. 前端提示只是临时补救

现在页面里提示：

```text
当前第一版后端还没有做级联删除保护，删除前先确认没有依赖数据。
```

这只能提醒用户，不能真正保证安全。

---

## 推荐升级方向

### Phase A：先做删除前检查

目标：

- 在后端删除前统计依赖数量
- 如果存在依赖，直接拒绝删除并返回明确错误

建议返回结构：

```json
{
  "detail": "Knowledge base has dependent data",
  "dependencies": {
    "documents": 3,
    "knowledge_items": 18,
    "chunks": 246,
    "conversations": 2
  }
}
```

这一阶段的特点是：

- 不做真实级联删除
- 先把“能不能删”说清楚

这是最稳的第一步。

### Phase B：前端展示依赖信息

目标：

- 删除弹窗里直接展示依赖统计
- 告诉用户为什么当前不能删

效果应该从现在的泛提示升级成：

```text
该知识库下还有：
- 3 个文档
- 18 个知识条目
- 246 个 chunks
- 2 个会话

请先清理依赖数据，再删除知识库。
```

这样用户不用猜。

### Phase C：决定最终删除策略

后面需要在这三种方案里选一个主策略：

#### 方案 1：强限制删除

规则：

- 只允许删除“空知识库”

优点：

- 最安全
- 最容易实现

缺点：

- 用户需要手工先删文档、条目、会话

#### 方案 2：级联删除

规则：

- 删除 knowledge_base 时，一并删掉下游依赖数据

优点：

- 用户操作简单

缺点：

- 风险最高
- 一旦误删，影响面很大

#### 方案 3：软删除

规则：

- 不真正物理删除
- 只把知识库标记为 `deleted` / `archived`

优点：

- 可恢复
- 更适合企业数据场景

缺点：

- 查询、检索、列表都要补过滤逻辑

---

## 我建议的顺序

先做：

1. 删除前依赖检查
2. 前端依赖提示
3. 再决定是否需要软删除

不要一上来就做物理级联删除。

原因很直接：

- 你这个项目已经有文档、chunk、会话、消息链路
- 级联删除一旦做粗，会把数据追溯能力直接砍掉
- 对企业知识库系统来说，这通常不是第一选择

---

## 更合理的长期方向

如果后面项目继续产品化，我更倾向于：

```text
默认软删除 knowledge_base
  -> 前端列表默认隐藏
  -> 检索链路过滤 deleted 数据
  -> 管理员可以恢复或彻底清除
```

这样会更像真实企业系统，而不是 demo 风格的“点一下就物理删掉”。

---

## 验收建议

后面做这项升级时，至少验这几种情况：

1. 空知识库删除成功
2. 非空知识库删除被拦截
3. 错误提示里能看见依赖统计
4. 前端弹窗能正确展示后端返回原因
5. 不会误删 Elasticsearch / PostgreSQL / 本地文件数据
