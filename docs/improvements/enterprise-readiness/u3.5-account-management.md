# U3.5：账号管理、会话安全与审计

U3 解决“用户如何登录”；U3.5 把它推进到可操作的账号中心：管理员可以管理当前组织成员，普通用户可以管理自己的密码和会话，系统能追溯关键身份动作。

U3.5 不替代 U4。U4 仍然负责把知识库、文档、ES 检索、OSS 上传和对话资源真正按 `organization_id` 隔离。

### token_version 的作用

JWT 除了 `jti`，现在还有 `ver`：

```json
{
  "sub": "42",
  "jti": "one-token-id",
  "ver": 3
}
```

用户表也保存当前版本：

```text
users.token_version = 3
```

每次鉴权会比较两者：

```text
JWT ver == users.token_version ?
  是 -> token 可继续走后续权限检查
  否 -> 401
```

所以修改密码、管理员重置密码、禁用账号、角色变化和“退出全部设备”都会递增版本。旧 token 不需要逐条写 Redis，也会立即失效。

它与 Redis `jti` 黑名单的区别：

| 场景 | 机制 | 粒度 |
| --- | --- | --- |
| 当前设备点击退出 | Redis `blacklist:{jti}` | 单个 token |
| 修改密码 / 退出全部设备 | `token_version` | 该用户全部旧 token |

## 权限边界

当前项目沿用现有 `user:manage` 权限：`owner` 和 `admin` 可以进入成员管理页。

但 owner 是组织最终控制权，因此增加了额外规则：

- 只有 `owner` 能创建或变更 owner 角色。
- `admin` 不能修改 owner、重置 owner 密码、禁用 owner 或移除 owner。
- 最后一个有效 owner 不能被禁用、降级或移除。
- 用户不能禁用或移除自己的当前账号。

在 PostgreSQL 中，这个“最后一个 owner”检查会对当前组织的 owner 关系行使用
`SELECT ... FOR UPDATE`。这样两个并发管理请求不会都基于同一份过期计数做判断：
先到的事务完成后，后到的事务才会继续，并重新看到最新有效 owner 数量。

这里体现了一个常见原则：RBAC 解决“能否进入某类操作”，业务规则解决“这个具体对象是否允许被这样操作”。

## 管理员接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/admin/users` | 当前组织成员列表 |
| `POST /api/admin/users` | 创建成员；当前第一版相当于管理员创建账号并邀请成员，不接邮件发送 |
| `PATCH /api/admin/users/{id}/role` | 修改组织角色 |
| `PATCH /api/admin/users/{id}/status` | 启用或禁用账号 |
| `POST /api/admin/users/{id}/reset-password` | 设置新密码并使旧 token 失效 |
| `DELETE /api/admin/users/{id}` | 移除组织成员；不物理删除用户和审计记录 |
| `GET /api/admin/audit-logs` | 查询安全审计日志 |

“移除成员”不是 `DELETE users`。真实企业系统通常需要保留用户 ID 和历史审计，删除的是组织关系；如果该用户没有其他组织关系，当前实现会顺带禁用账号。

## 个人账号接口

| 接口 | 用途 |
| --- | --- |
| `GET /api/auth/me` | 查看当前个人与组织身份 |
| `POST /api/account/change-password` | 验证旧密码、更新 Argon2 hash、递增 token version |
| `POST /api/account/logout-all` | 递增 token version，使全部旧 token 失效 |
| `POST /api/auth/logout` | 把当前 token 的 `jti` 写入 Redis 黑名单 |

## 审计链路

会记录：

```text
auth.login.success
auth.login.failed
auth.logout
account.password.change
account.sessions.revoke_all
admin.user.create
admin.user.role.update
admin.user.status.update
admin.user.password.reset
admin.user.membership.remove
```

审计日志不记录明文密码、password hash、JWT、API Key 或 Redis key。`details_json` 只保存必要的非敏感上下文，例如角色变化前后值。

## 前端结构

```text
AuthGate
  -> GET /api/auth/me
  -> AuthProvider 保存当前 user / organization / role
  -> AppFrame 根据 role 显示导航
       -> /admin/users  成员管理与安全审计（owner/admin）
       -> /account      我的账号（所有已登录用户）
```

`AuthGate` 是体验层保护；管理员接口仍使用 FastAPI `require_permission("user:manage")` 在后端执行真实授权。

## 本地使用

先迁移数据库并保证 Redis 已启动：

```bash
cd backend
bash scripts/migrate_database.sh upgrade
bash scripts/start_redis_local.sh
```

前端登录后：

1. owner/admin 从左侧进入“成员管理”。
2. 创建成员时设置初始密码；第一版不发送邮件。
3. 普通成员从“我的账号”修改密码或退出全部设备。
4. 在成员管理的“安全审计”标签查看登录、退出和管理操作。

## 当前边界和后续项

- 当前是单组织运行，尚未做组织创建、组织切换或邮件邀请。
- 管理员创建成员仍需通过安全渠道交付初始密码；后续可升级为一次性邀请 token + 邮件服务。
- 安全审计目前写 PostgreSQL；后续 U7 会接入结构化日志、request ID、告警和保留策略。
- 当前只对账号管理 API 做了 U3.5 RBAC；U4 会把同样的组织边界接入所有知识库业务资源。
